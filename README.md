# Smart Reading & Writing Assistant (NLP Pipeline)

A lightweight, mini-Grammarly-style assistant that takes a raw paragraph of
messy student text and runs it end-to-end through five classic NLP pipeline
stages: **spell checking → syntactic processing → semantic analysis →
discourse & pragmatic processing → full pipeline assembly**.

## How to run

```bash
# 1. Install dependencies
pip install -r requirements.txt --break-system-packages   # (drop the flag if not needed)

# 2. Download the spaCy model and NLTK data (one-time setup)
python3 -m spacy download en_core_web_sm
python3 -c "import nltk; [nltk.download(p, quiet=True) for p in \
  ['wordnet','omw-1.4','punkt','punkt_tab','averaged_perceptron_tagger', \
   'averaged_perceptron_tagger_eng','brown','stopwords','words']]"

# 3. Run the full pipeline on the 10 provided test samples
python3 pipeline.py
# -> prints the summary table and writes one JSON file per sample to outputs/

# 4. Run on your own text
python3 pipeline.py --text "Your raw messy paragraph here."

# 5. Run on a different folder of .txt samples
python3 pipeline.py path/to/your/folder

# 6. Stretch goal -- live spell-check-as-you-type demo
streamlit run app.py
```

Each stage can also be run and demoed independently:
```bash
python3 stage1_spellcheck/spellcheck.py
python3 -m stage2_syntax.syntax
python3 -m stage3_semantics.semantics
python3 -m stage4_discourse.discourse
```

## Repo structure

```
stage1_spellcheck/   spellcheck.py       -- from-scratch Levenshtein/Damerau-Levenshtein spell checker
stage2_syntax/        syntax.py          -- spaCy dependency parse + POS tags
                       cfg_parser.py      -- hand-built CYK chart parser over a custom 12-rule CFG
stage3_semantics/     semantics.py       -- NER, rule-based SRL over dep tree, from-scratch Lesk WSD
stage4_discourse/     discourse.py       -- heuristic coref, discourse connectives, pragmatic inference
stage5_pipeline/      pipeline.py        -- process(raw_text) wiring stages 1-4, run_on_folder(), summary table
pipeline.py                              -- top-level CLI entry point (as requested by the brief)
data/word_freq.json, bigrams.json        -- dictionary + n-gram LM built from NLTK Brown corpus (+ words corpus)
data/test_samples/                       -- 10 short "messy" real-world text samples (typos, ambiguous pronouns, informal grammar)
outputs/                                 -- per-sample JSON results + summary_table.json (generated by running pipeline.py)
app.py                                   -- stretch goal: Streamlit live spell-check demo
```

## Per-stage notes (what each stage demonstrates)

**Stage 1 — Spell Checking.** Implements Damerau-Levenshtein edit distance
entirely from scratch (a full DP table, including the adjacent-transposition
rule that turns common typos like "recieve" into a distance-1 edit) and
ranks candidates against a ~250k-word frequency dictionary built from the
NLTK Brown + Words corpora. When multiple candidates tie on edit distance
(or a word is in a confusable set like there/their), a bigram language
model built from Brown is used to pick the correction that best fits the
surrounding words, and every change is reported with its reason (raw
edit-distance score or n-gram probability).

**Stage 2 — Syntactic Processing.** Uses spaCy to produce a real dependency
parse tree and POS-tag sequence for every sentence. In parallel, a
hand-written CYK chart parser (bottom-up DP over spans, with unary-rule
closure) parses the same sentence against a small custom 12-rule CFG,
demonstrating the parsing algorithm itself rather than just calling a
library; it successfully parses simple declaratives and reports "no parse"
gracefully when a sentence falls outside its intentionally small grammar.

**Stage 3 — Semantic Analysis.** spaCy's NER extracts named entities, and a
hand-built rule set walks each sentence's dependency tree (nsubj → agent,
dobj/dative → patient/recipient, ROOT verb → action, prep children →
modifiers, including a passive-voice swap) to build "who did what to whom"
frames without a trained SRL model. A from-scratch Lesk algorithm — overlap
between the sentence's context words and each WordNet sense's gloss/examples
— disambiguates ambiguous words such as "bank", "bat", "light", and "book".

**Stage 4 — Discourse & Pragmatic Processing.** Since a pretrained coref
model wasn't reliably available offline, a hand-built nearest-antecedent
heuristic resolves pronouns using gender/number agreement tables; it works
well for clear cases (Sarah → she) but, like any heuristic resolver, can
mis-attach ambiguous "it" references when several same-gender candidates
are nearby — a known and documented limitation rather than a hidden one. A
hand-built connective list tags discourse relations (contrast/cause/
elaboration/temporal/condition), and one pragmatic rule detects indirect
requests ("Could you review it?" → recognized as a request, not a literal
yes/no question).

**Stage 5 — Full Pipeline Assembly.** `process(raw_text)` in
`stage5_pipeline/pipeline.py` wires Stages 1→4 into one function: text is
spell-corrected first, then parsed, semantically analyzed, and run through
discourse/pragmatics on the corrected text. `run_on_folder()` processes all
10 test samples, writes one JSON file per sample to `outputs/`, and builds
the required summary table of corrections/entities/coref chains/discourse
relations per sample (see `outputs/summary_table.json` after running).

## Known limitations (documented honestly)
- The CFG in Stage 2 is intentionally tiny (12 rules); it only covers
  simple declarative sentences and will correctly report "no parse" on
  anything more complex — spaCy's dependency parser is the "always works"
  path, the CYK parser is the from-scratch mechanics demo.
- Coreference resolution is a heuristic (nearest gender/number-compatible
  antecedent), not a trained coref model, so it can pick the wrong
  antecedent when several compatible candidates are close together.
- The context-aware spell corrector relies on bigram statistics from a
  general-purpose corpus; on highly ungrammatical fragments (e.g. "might of
  to reschedule") it can occasionally mis-correct a function word, since
  local bigram evidence for the garbled phrasing is sparse or misleading.
